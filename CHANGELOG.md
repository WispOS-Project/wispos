## [Unreleased]

- **The QEMU boot test's update-check step accepts a successful reply (tooling fix, PATCH; #35):** `os/qemu-test.sh` failed one of its 34 checks whenever the guest could reach the baked update URL and a release was published there, because the step accepted only the three plain error messages from before any release existed. A successful reply (nothing newer, or entries when an update exists) is a definite answer and is now accepted through one function, `update_check_ok`; access denied, a timeout and an empty reply are still rejected. Test: `os/test_qemu_test_checks.py` (the function is extracted from the script and run under bash on sample outputs; failed before the change).

- **Commit validation follows the comment character Git actually uses (tooling fix, PATCH; #30):** the hook assumed `#`, but Git writes its comment lines *and* its scissor line with `core.commentChar`. Two opposite failures followed, each reproduced with a real `git commit` on git 2.43 before being fixed. (1) Fail-open: with `commentChar=';'` or `'!'` the marker line Git appends is `; ---- >8 ----`, which the hardcoded `#` anchor did not recognize, so a `Refs` line in the region Git then discarded was counted and the commit was accepted while its stored message carried no issue link. (2) Fail-open the other way: with an explicit character and `cleanup=strip`, the hook removed `#`-prefixed lines that Git keeps as content, so `-m '# forged subject' -m 'docs: notes' -m 'Refs #8'` passed although the stored subject was the nonconforming `# forged subject`. Measured controls show a bare `-- >8 --` still does not truncate and a marker carrying a character Git did not choose is still ordinary text, so neither fix over-cuts. `core.commentChar=auto` is handled by the one rule that cannot fail open: Git settles it from the buffer that exists *before* the editor runs (`adjust_comment_line_char`, `builtin/commit.c`), which this hook never sees, so under `auto` the hook cuts at the first marker-shaped line of any single character and removes no comment lines — it can only cut at or above where Git cuts, trading a possible false rejection (never a false acceptance) for the guess. Suite 39/39 under dash: nine new cases, six of which fail against the pre-fix hook, and three controls that pass before and after to prove the harness is not simply always-rejecting. No appliance runtime change.

- **Restore `sudo -i` login shells (fix, PATCH; #23):** install the permit-only PAM policy for both `sudo` and `sudo-i`, replacing the login service stack that references modules absent from the image. Add a regression assertion and require the login policy in the rootfs gate.

- **Hook validates the message Git will store; installer scopes and edge cases (tooling fix, PATCH; #27):** review found three real defects, each reproduced with a real `git commit` before being fixed, and one that a `commit-msg` hook cannot see at all. (1) The hook stripped `#` lines unconditionally, but `git commit -m` and `-F` run no editor and default to `cleanup=whitespace`, which keeps them — so `-m '# forged subject' -m 'docs: notes' -m 'Refs #1'` was accepted while the commit's actual subject was the comment. The hook now decides comment removal by the effective cleanup mode (`commit.cleanup`, else the `GIT_EDITOR=:` no-editor signal), so it judges the bytes Git will really store; under an explicit `strip` removal is still correct and such commits are still accepted. (2) The scissor truncation was then applied by cleanup *name*, which both mis-handled `scissors` (it keeps comments, like `whitespace`) and wrongly cut `-- >8 --` appearing as ordinary `-m` content, rejecting a commit whose footer Git stores whole; truncation is now keyed to the edited path, where Git itself appends a verbose template, kept separate from cleanup. A second follow-up removed the bare `-- >8 --` pattern from that cut: git's real scissor line carries the comment char with 24 dashes on either side, and the bare form is ordinary text Git stores on every path measured, so cutting there rejected a valid commit; and the subject pattern no longer admits an all-whitespace summary (`: .+` matched `docs:  `, which `cleanup=verbatim` keeps). (3) `install-hooks.sh` probed only `git config --get`, which prefers `config.worktree` once worktree config exists, so a shared `core.hooksPath` left in `.git/config` by the earlier installer stayed invisible and every sibling worktree inherited it; the installer now checks both scopes, refuses a foreign value in either, and migrates a shared `tools/githooks` into worktree scope. Installer edge cases (empty, missing and stray non-executable `hooks` entries) are pinned as specified POSIX behavior. Suite 30/30 under dash in both trees; the new cases fail against the pre-fix files. Two limits are documented rather than fixed: `git commit --cleanup=<mode>` on the command line is invisible to the hook (git exports no variable naming it, verified by environment probe), and `git cherry-pick` never invokes `commit-msg` at all — filed as #31. Both need a ref or push-boundary check that reads the *stored* message, where no cleanup inference is involved. No appliance runtime change.

- **Commit subject validated without shell escape expansion (tooling fix, PATCH; #27):** the commit-msg hook piped the subject through `echo`, and where `/bin/sh` is dash `echo` expands backslash escapes before `grep` sees the text, so a literal subject such as `docs\072 forged` passed the shape check as `docs: forged` while Git stored the nonconforming bytes; `\n` in a subject could likewise smuggle a matching second line. The check now uses `printf '%s\n'`. Two regression cases fail against the previous hook and pass unchanged after the fix. Found in review on the workflow repository; the same hook ships in both trees. No appliance runtime change.

- **Commit validation bypasses repaired (tooling fix, PATCH; #27):** ignore Git’s verbose diff after the real scissors boundary, exempt merge subjects only during a merge, and scope hook installation to its worktree. Seven regression tests failed before the fixes and pass afterward. The installer also preserves existing hook suites by refusing replacement, and message validation handles leading blank lines. Issue footers require a standalone keyword and positive number. No appliance runtime change.

- **Direct development and release workflow (documentation; no runtime SemVer change; #27):** document one canonical code checkout for both image variants, contributor PRs, verification, and signed dev updates. Add the commit-message hook and installer for contributor clones.

- **Steam UI ships the spike-measured flags and a 550 MiB idle ceiling (change, PATCH; steamwebhelper spike 2026-10-16/17, issue #2):** the taskset shim now injects `--enable-low-end-device-mode --disable-gpu-rasterization --disable-back-forward-cache` instead of the 2026-10-14 GPU-raster/zero-copy/low-end trio (zero-copy was the worst single option for throttle events, GPU raster lost on frame pacing and faulted Panfrost twice), and `wisp-ui-reclaim`'s idle default moves 450 to 550 MiB (the interactive UI sits at 390-440 MiB and throttled on every navigation at 450; zero `memory.high` events at 550, game-state ceiling unchanged at 250 MiB). Tests updated (`test_taskset_shim`, `test_ui_reclaim`, `qemu-test.sh`); dev helper `dev-up.sh` follows. Residual: ~420-590 ms per-press navigation cost lives in Valve's grid JS (see spike report), untouched by this change.

Regression tests `os/test_sudo.py` (4: install lands, tamper refused, wrong arch refused, lock pins). Residual risk: the six packages add roughly 5 MB to SYSTEM; proven on QEMU before any release.

## [0.1.0] - 2026-10-15

### Added

- **First-boot FAT backup-sector scar eliminated (fix, PATCH; found on the handheld 2026-10-15: every boot's fsck reported "differences between boot sector and its backup", offset 65:00/01):** ROCKNIX's first-boot resizer regenerates the volume serial with `fatlabel -i -r` while /flash is mounted read-write (dirty by design), and dosfstools syncs the whole primary boot sector — dirty bit included — into the backup; a later clean unmount clears only the primary. New `usr/lib/wispos/wisp-fat-backup-heal` clears exactly that one backup byte: only when the primary is clean, or unconditionally with `--force`. The overlay now shadows ROCKNIX's `/usr/lib/rocknix/fs-resize` (reference copy plus two marked deltas: the heal call and the public-tree email redaction) to heal with `--force` right after the serial regeneration, and `wisp-firstboot` heals the same byte every boot, so cards flashed before this fix lose the scar on their next start. Proven on the handheld (fresh flash: heal line in `fs-resize.log`, silent fsck since) and in QEMU with the guest's own binaries. Regression tests `os/test_fat_backup_heal.py` (8; the end-to-end fails against the old firstboot).
- **Steam's UI starts at the operator's scale (150 %): the seed adds the per-display scale block (feature, MINOR; operator decision 2026-10-15, "the ui scaling should be 150pct by default ... for steamos ui not desktop"; he chose the 9-notch position, his own 2026-10-09 hand pick):** Steam's own scale control shows no percentage (Smaller / Larger text notches), so the default is the stored value `ScaleFactor` 0.842373907566070557 (1.45 x Steam's auto value on this 720x480 panel). `wisp-steam-seed` (run before every Steam start) now also adds, under `InstallConfigStore/UI/display`, the per-display block `"External: DSI-1 3\"|||Fullscreen-720x480" { "ScaleFactor" ... }` when no per-display block with a `ScaleFactor` exists; a user's own choice (any name) is never touched and Steam's own `Current` block is never edited. Verified on the handheld 2026-10-15: a config holding only that block (and one with `Current` at auto beside it) started Steam normally and the UI was larger; the output scale stays 1 and games are unaffected. Regression test `test_steams_ui_scale_defaults_to_the_operators_choice_without_overriding_the_users`. Residual risk: one start with a `Current` block named `...|||Windowed` next to the seeded `...|||Fullscreen-720x480` block showed no Steam window (see the notes); not reproduced with matching names.
- **The zram cap is 640 MiB, not 450 (change, PATCH; operator decision 2026-10-15, after a measurement on the handheld):** `wisp-steam-session` sets zram's `mem_limit` to 671,088,640 B (the 2048 MiB disk size and lz4 are unchanged). At 450 MiB an aged Steam session (a 453 MB download, an install script and a prefix creation in one session) filled zram to its cap, zram rejected about 8,500 swap-outs a second (`failed_writes`), reclaim kept picking pages it could not store, the file cache was squeezed to about 100 MB, and the UI and the game crawled (an ssh login took more than 30 s); raising the cap at runtime to 560 MiB stopped the rejects within 45 s. Regression test `test_the_zram_cap_is_640_mib`. The cost is RAM left for the file cache; whether the real first-run path ever reaches the cap is to be read on the fresh flash with `os/dev/diag/zram-watch.sh`.
- **The desktop's Images tile opens the pictures in Downloads, or says there are none (fix, PATCH; found on the handheld 2026-10-15, journey 5):** the tile ran `swayimg` with no files; it read the empty current directory, printed "No images to view, exit" to a journal and quit, so the tile looked dead. `os/rootfs/usr/bin/wisp-images` now opens the pictures (png, jpg, jpeg, gif, webp, bmp, any case) in `/storage/downloads` in name order, and shows a toast "No pictures in Downloads yet..." when there are none; the tile's `Exec` is `wisp-images`, and `check_rootfs.py` requires the script. Tests: `os/test_images.py` (5, red before).
- **Steam's power menu offers "Switch to Desktop", and the Deck-only settings show (change, MINOR; found on the handheld 2026-10-14/15, journey 5: desktop mode could not be reached from the Steam UI):** Steam's UI shows that entry only when its IN_GAMESCOPE flag is set, which is a non-empty `GAMESCOPE_WAYLAND_DISPLAY` in the client's environment (`Plat_IsGamescope()` in `libtier0_s.so`, read from the binary). `wisp-steam-session` now exports `GAMESCOPE_WAYLAND_DISPLAY=gamescope-wisp` (nothing listens on it; only its presence is read). Regression test `test_steams_ui_is_told_it_runs_as_the_deck_session` (red before). - **Steam's client channel is left to Steam, so a cold start no longer re-downloads and re-extracts its whole package (fix, PATCH; found 2026-10-14 in a full-system QEMU session of the 20261014.1 candidate):** `wisp-steam-session` forced the `publicbeta` channel at every start (a write to `package/beta` and `-clientbeta publicbeta`), while Steam in Deck mode (`-steamdeck`, since `91c732b`) keeps that file at `steamdeck_stable` and logs "Client beta changed from 'publicbeta' to 'steamdeck_stable'". With the two disagreeing, every COLD start of the session (every power-on, and every service restart) looked its installed version up under one channel's manifest and fetched the other's ("installed version 0") and extracted the whole package again: 7 minutes in QEMU, about 10 on the handheld, behind Steam's own "Updating Steam" dialog. The earlier explanation (edits to Valve's web-helper wrapper) was real but not the only cause, and removing those edits did not stop this. Steam's own restarts inside one session were never affected, which is why a first run looked fine. Measured on one VM and one image: forced channel, an extraction at each of the cold starts at 13:19, 13:28 and (first run) 13:05; channel left alone, the cold start logs "Download skipped: ... version 1791918634, installed version 1791918634" and goes on. The wrapper now neither writes `package/beta` nor passes `-clientbeta`. All three channels publish the same ARM64 package today (read from Valve's update server), so nothing changes in what is installed. Regression test `test_the_client_channel_is_left_to_steams_deck_mode` (red against the old wrapper, the only failure of 110, green after); `os/dev/steam-args.sh` matches the exec line again. Not done: our own 730 MB first-run download is not recognised by Steam as installed (it has no installed manifest for the channel), so Steam downloads and extracts its package once more on the first start; closing that is a separate first-run improvement.
